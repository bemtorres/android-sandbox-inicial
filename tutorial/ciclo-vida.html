Fundamentos Ciclo de vida

🔄 Ciclo de vida de Activity

Si estás estudiando Android Activity, onCreate() es solo una parte del ciclo. Estos son los métodos principales que debes conocer — el orden normal es onCreate → onStart → onResume → [usable] → onPause → onStop → onDestroy.

Método ¿Cuándo ocurre? Uso típico
onCreate() Se crea la Activity Inicializar UI, variables, listeners
onStart() Empieza a ser visible Preparar recursos visuales
onResume() Usuario puede interactuar Cámara, sensores, iniciar procesos
onPause() Pierde el foco Pausar, guardar cambios rápidos
onStop() Ya no es visible Liberar recursos
onDestroy() Se destruye Limpieza final
onRestart() Vuelve tras onStop() Preparar nuevamente

Ejemplo completo con logs — Java y Kotlin

public class MainActivity extends AppCompatActivity {
    @Override protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_main);
        Log.d("CICLO", "onCreate");
    }
    @Override protected void onStart() { super.onStart(); Log.d("CICLO", "onStart"); }
    @Override protected void onResume() { super.onResume(); Log.d("CICLO", "onResume"); }
    @Override protected void onPause() { super.onPause(); Log.d("CICLO", "onPause"); }
    @Override protected void onStop() { super.onStop(); Log.d("CICLO", "onStop"); }
    @Override protected void onRestart() { super.onRestart(); Log.d("CICLO", "onRestart"); }
    @Override protected void onDestroy() { super.onDestroy(); Log.d("CICLO", "onDestroy"); }
}

    override fun onStart() { super.onStart(); Log.d("CICLO", "onStart") }

⭐ Los más importantes para aprender primero

1. onCreate → construir · 2. onStart → visible · 3. onResume → interactuando · 4. onPause → pierde foco · 5. onStop → no visible · 6. onDestroy → destruida · 7. onRestart → vuelve desde onStop().

Otros: onBackPressed / OnBackInvokedDispatcher, onSaveInstanceState(), onRestoreInstanceState(), onNewIntent().

Casos reales Qué puede pasar

Qué puede pasar en el ciclo — 7 casos con logs

No basta con saber el orden. Abre Logcat filtrado por CICLO y reproduce cada caso. Si no liberas en el método correcto, tendrás leaks, cámara bloqueada o datos perdidos al rotar.

Caso 1 — Lanzar app por primera vez

Tap en icono

onCreate() → onStart() → onResume()
[ACTIVITY USABLE]

Qué hacer: `setContentView`, `findViewById`, `init listeners` solo en `onCreate`. Log: onCreate / onStart / onResume

Caso 2 — Pulsar Home (app a segundo plano)

Home → launcher

onPause() → onStop()
[NO VISIBLE]

Qué hacer: pausar video/cámara en `onPause`, liberar sensores en `onStop`. Si no, la cámara queda bloqueada para otras apps.

Caso 3 — Volver desde Recientes

Tap en tarjeta de recientes

onRestart() → onStart() → onResume()
[USABLE DE NUEVO]

Qué pasa si no manejas: Si liberaste en `onStop`, debes re-crear en `onRestart/onStart`. Log: `onRestart` solo aparece aquí.

Caso 4 — Rotar pantalla (¡crítico!)

Girar dispositivo

onPause() → onStop() → onSaveInstanceState() → onDestroy()
→ onCreate(savedInstanceState) → onStart() → onResume()

Qué pasa: Activity se destruye y recrea. Sin `onSaveInstanceState` pierdes datos del formulario. ViewModel sobrevive, Activity no.

@Override protected void onSaveInstanceState(Bundle outState){
    super.onSaveInstanceState(outState);
    outState.putString("email", etEmail.getText().toString());
}
@Override protected void onCreate(Bundle savedInstanceState){
    super.onCreate(savedInstanceState);
    if(savedInstanceState != null){
        String email = savedInstanceState.getString("email");
    }
}

Caso 5 — Pulsar Back

Back del sistema

onPause() → onStop() → onDestroy()
[DESTRUIDA, sale del stack]

Si era la única Activity, app a background. `finish()` provoca el mismo flujo.

Caso 6 — Llamada / Diálogo de permiso

Otra app roba foco pero no tapa del todo

onPause() → [semi-visible] → onResume()

Solo `onPause/onResume`, sin `onStop`. Pausa audio/cámara aquí, no en `onStop`.

Caso 7 — Sistema mata app en 2º plano

Falta de memoria

onStop() → onDestroy() // sin onSaveInstanceState si no lo implementas
Al volver: onCreate(null) → pierdes todo

Solución: persiste en `Prefs/DataStore` o `ViewModel + SavedStateHandle` para datos críticos.

Qué puede fallar si ignoras el ciclo

  • Cámara/sensor no liberado en `onPause` → otras apps no pueden usarlo, batería drenada.
  • `Handler.postDelayed` sin `removeCallbacks` en `onStop/onDestroy` → leak y crash al volver.
  • Formulario sin `onSaveInstanceState` → al rotar se borra el email escrito.
  • Registrar `BroadcastReceiver` en `onStart` y no desregistrar en `onStop` → leak.

Regla de oro Sandbox

En este proyecto: `onCreate` = `setContentView + findViewById + listeners`, `onDestroy` = `handler.removeCallbacks` (Lab 5), `onSaveInstanceState` = guardar email si quieres. El resto solo `Log.d` para ver el flujo en Logcat.

@Override protected void onDestroy(){
    super.onDestroy();
    handler.removeCallbacks(progressRunnable);
    Log.d("CICLO","onDestroy + limpieza");
}
